# wsindex тому, кто решает, может ли код уходить наружу

## Короткий ответ

По умолчанию не уходит ничего: ни телеметрии, ни исходников, ни запросов.
Модель эмбеддингов работает в том же процессе, который индексирует, индекс
— файл рядом с конфигом, а прогретый поиск открывает **ноль сокетов**;
это измерено, а не заявлено.

Изменить это могут три вещи, и ни одна не является умолчанием. Каждую
нужно вписать в конфиг руками, и каждая названа ниже вместе с тем, что
именно она отправляет.

## Что открывает сокет и когда

| Когда                               | Что уходит                               | Избежимо                   |
| ----------------------------------- | ---------------------------------------- | -------------------------- |
| Первая индексация на машине         | Модель качается с хоста моделей (~90 МБ) | Да — заранее наполнить кэш |
| Все последующие индексации и поиски | Ничего                                   | —                          |
| `wsindex sync` на репе с `remote`   | То, что отправляет `git fetch`           | Только не пользоваться     |
| `[embeddings] provider = "remote"`  | **Каждый чанк каждой репы**              | Да — выключено             |
| `[rank] provider = "remote"`        | Запрос и ~40 чанков-кандидатов на поиск  | Да — выключено             |
| `wsindex serve`                     | Слушает сокет, который вы велели слушать | Да                         |

Модель качается однократно, дальше офлайн: при загрузке сначала
проверяется локальный кэш и только потом сеть.

## Две удалённые опции — это разные решения

**Удалённый эмбеддер** отправляет весь корпус, один раз при индексации и
снова при каждой переиндексации. Шестнадцать тысяч чанков для небольшого
пространства.

**Удалённый переранжировщик** отправляет запрос и кандидатов, которых
поиск уже нашёл, — около сорока чанков, и только связанных с тем, что
спросили. На три порядка меньше, и индекс не покидает машину.

Если у вас просят качество хостинговой модели, давать почти всегда стоит
второе: измерено, оно даёт те же 13 из 16 на идентификаторных вопросах,
что и замена эмбеддера целиком.

Обе называют ключ через `token_env` — **имя переменной окружения, а не
сам ключ**. Ключ в конфиге это ключ в чьей-то истории git. Незаданная
переменная сообщается по имени, а не чужим 401.

## `trust_remote_code` выключен, и это решение по безопасности

Ряд моделей эмбеддинга и переранжировки везут собственный Python и ждут,
что его исполнят при загрузке. Это произвольный код с хоста моделей,
исполняемый в процессе, который читает ваши исходники. Выключено по
умолчанию, включается явно и на каждое пространство отдельно.

Наблюдение из эксплуатации в пользу того же решения: из пяти
опробованных моделей, которым это нужно, **не загрузилась ни одна** —
сломана обновлением библиотеки, не хватает пакетов или просит десятки
гигабайт. Все модели, не везущие своего кода, заработали.

## Сервер, если команда поднимает общий

- **Аутентификация — bearer-токен**, названный в конфиге через переменную
  окружения. Чтобы слушать публичный адрес без него, нужен флаг
  `--insecure`, названный так намеренно.
- **Токен принадлежит серверу, а не человеку.** Личности нет, и это
  сознательно: завести её значило бы завести аутентификацию по людям
  **и** журнал чужих вопросов, приписанных к именам. Журнал поиска не
  пишет личности, админка показывает только агрегаты.
- **Следствие, которое надо произнести вслух:** кто держит токен, тот
  ищет по всему, что сервер проиндексировал. Если в пространстве
  смешаны репозитории с разной аудиторией, поднимайте разные серверы, а
  не рассчитывайте на разграничение, которого нет.
- Эндпоинты: `/search`, `/index`, `/status`, `/healthz`, `/metrics`. В
  метриках нет текста запросов — только метки маршрутов.

## Что лежит на диске

Индекс живёт рядом с конфигом (или там, где указывает `[store] uri`). В
нём текст каждого проиндексированного чанка, его путь, диапазон строк и
вектор — то есть **индекс настолько же чувствителен, как исходники, из
которых собран**. Относитесь к нему так же, выбирая, где он лежит и кто
его читает, — особенно если `uri` указывает на общее хранилище.

`wsindex stats` держит локальный журнал запросов этой машины. Он локален
по построению и никогда не пишется в хранилище ссылок, потому что то
может быть общим Postgres, а чужие вопросы в командной базе не место.

## Как проверить всё это самому

```console
$ wsindex status                     # что настроено и где лежит индекс
$ grep -n 'provider\|token_env\|url' wsindex.toml   # всё удалённое видно здесь
```

Ничего выше не требует веры на слово, но будьте точны в том, что каждое
свидетельство покрывает. `test_searching_opens_no_sockets` прогоняет путь
поиска — включая запись, которая его фиксирует, — и падает, если что-то
соединяется; **его собственный docstring говорит, чего он не доказывает**,
потому что он идёт на фейковом эмбеддере и про настоящую модель не
говорит ничего. Та проверялась отдельно: прогретый поиск с настоящей
моделью открыл ноль сокетов. Утверждение составляют оба замера, ни один
из них сам по себе.

Конфиг — единственное место, где можно назвать удалённый эндпоинт, а
значит `grep` по `wsindex.toml` это полный аудит того, куда инструмент
вправе обращаться. Вот эта часть веры не требует вовсе.
